# Call and application performance repair — 11 September 2026

This release is for the separate Telnyx application and its Frankfurt Supabase/Vercel projects. It does not change the original dispatch production system. Database incident remediation, application read/save changes and voice recovery are released separately through `dev`, then `main`.

## Incident and observed recovery

Business conflicts raised PostgreSQL `40001`, a serialization-retry code, instead of a domain conflict. The observed database was repeatedly rolling back about 1,400 transactions per second. The SQLSTATE repair maps these deliberate conflicts to `PT409` while preserving actual serialization failures and compatibility with clients that understand either code. See [SQL remediation](sql-conflict-remediation-2026-09-11.md).

The first release, PR161/162, reached production and its migration was applied to the copy. Three consecutive observation intervals, each at least 60 seconds, covered 345.65 seconds with **zero additional rollbacks**, no queued locks and no looping case RPC. A later read at 19:16 UTC still showed the same rollback counter. At 19:40 the counter was 14,086 higher and remained unchanged in the next observation; there was no active loop or lock queue. A wider catalog check found two remaining deliberate `40001` exceptions in the private reminder-delivery trigger. Their causal contribution to that intervening increase is unproven; a separate targeted forward migration addresses the same retry hazard. No database restart or process termination was necessary. This is evidence that the observed retry incident stopped; it is not a CPU/RAM capacity measurement.

## Resulting behavior

- A case save commits atomically with its mutation UUID, input fingerprint and revision. A retry after a lost response recovers that exact result. Reusing the UUID with different input is rejected. New clients receive the changed case instead of reloading the whole dispatch dataset. Existing open clients retain their response contract. [Case save and refresh contract](case-refresh-reconciliation.md).
- Fleet refresh returns a fleet DTO. Optional attendance, access administration and call history load when needed. Repeated reads share an in-flight request and use actual cancellation signals. Existing draft/version guards prevent late reads from replacing newer edits.
- Webhook delivery, contention deferral, waiting for correlation and actual effect failure have separate counters and deadlines. Completion uses the exact claim timestamp. A terminal result cannot be overwritten by a stale invocation. [Webhook retry contract](webhook-retry-contract.md).
- Startup stores its frozen dial and a durable obligation to create the local leg/history before dispatch. HTTP retries and cron can finish an accepted call without another provider dial, even when webhooks never arrive. Unknown media outcomes retain their original command and watchdog; replacement speech requires a definite provider rejection.
- New voice sessions can use a fixed ownership generation enforced by database triggers and an immutable provider command journal. A lost response never authorizes a blind second dial. Exact provider events can reconcile supported operations. Old writers cannot mutate a session admitted under the new contract. [Voice ownership and recovery contract](telephony-command-contract-v2.md).
- For calls with a frozen recording-disabled policy, answer/bridge runs before auxiliary call-history projections. Projection failure retains a durable recovery obligation and cannot compensate a working bridge. Replayed history derives current status/ownership, and delayed fairness timestamps cannot move backwards or become artificially recent. Callback confirmation still requires its callback to have been committed first.
- Authentic provider leg facts can advance while an older command remains unresolved. Urgent teardown runs before failed bookkeeping. Hangup intent is durable before waiting for ownership; each late accepted leg has independent cleanup and retry through the existing five-minute cron.

No worker, listener or additional scheduler is introduced. Recording/privacy prerequisites remain in force for sessions whose frozen policy requires them. Ring fanout remains serial: changing its concurrency is deferred until representative healthy-provider measurements justify that additional change.

## What the measurements mean

Browser timing is local User Timing data, with bounded retention and UUID correlation between startup, microphone, registration, HTTP response, exact operator invite, answer, active state and audio-element `playing`. Provider IDs, phone numbers, SDP and media are excluded from these timing entries. HTTP request IDs join browser measurements to server logs. An audio element playing is not proof of audible, bidirectional speech.

Server measurements expose handler duration and aggregate auth, database request, lease, provider and checkpoint spans. Database transport spans measure response headers; provider attempt spans include the body. Counts reveal repeated roundtrips. Response byte count is reported only when a `Content-Length` is available; an absent count is unknown. Spans may nest or overlap, so their durations must not be summed as independent time.

Isolated Chrome measurements used trusted clicks with intercepted network/SDK behavior: 50 feedback samples had p95 **30.4 ms** and 30 dial-to-mocked-acknowledgement samples had p95 **17.2 ms** in the final browser run. They verify UI behavior only. Five fresh local Node processes imported the built webhook route in **174–250 ms**, median **186 ms**, with network access disabled. Neither result measures live Vercel cold starts, Telnyx call setup or speech latency.

## Validation and release gates

The implementation was independently reviewed; gaps in provider-fact ordering, stale projections, projection ownership, termination recovery, unknown media outcomes and startup materialization were corrected before approval. Native tests include real disposable PostgreSQL/PostgREST races, lost provider-response tests, simultaneous startup identity conflicts, webhook claim races and adversarial Chrome interactions. Final local gates passed: 3,583 Vitest tests (two existing optional skips), all 60 native Node checks with isolated PostgreSQL enabled, 67 Chrome scenarios, 11 fencing groups, eight webhook SQL tests, 18 case SQL tests and seven private reminder SQL/PostgREST tests. Typecheck, changed-code ESLint with zero warnings and the production build passed. The normal full test, typecheck and build gates also run in Vercel Preview.

The additive voice migration initially leaves `motorist_telephony_writer_rollout.new_session_contract = 1`. Enable `2` only after the compatible code is verified on this project's dev and production deployments. Existing sessions keep their original contract. Rolling back admission to `1` does not remove protection from an existing contract-2 session; never roll application code back to a writer that cannot handle those sessions. Do not restore deliberate `40001` exceptions or delete mutation receipts/provider evidence during rollback.

Live Telnyx configuration inspection, two-way speech, representative 30-sample call/save/refresh distributions and CPU/RAM/pool time series remain separate acceptance evidence. They are not inferred from isolated tests, one health request or an empty error-log query. No shared-project load test or call to an unverified number is used to fill these gaps.
