# Private reminder conflict companion

Migration `20260929210000_private_reminder_conflict_sqlstate.sql` changes only the two deterministic `40001` errors in `app_private.motorist_validate_reminder_delivery()` to `PT409`. The enabled trigger runs before reminder notification inserts; it rejects a missing task or a stale generation/recipient after locking the task and reminder. These business refusals must finish with a PostgREST HTTP409, without automatic serialization retries.

The migration checks the complete canonical definition against normalized MD5 `2e89c224a761d506da56da04f32896f8`, audited against this copy on2026-09-11. Missing or drifted definitions stop the transaction. Reapplying an otherwise identical patched definition is safe. CREATE OR REPLACE retains function identity, owner and grants; all body text except the two error literals, SECURITY DEFINER, search_path, task/reminder locks, trigger metadata and table RLS remain unchanged. The ten public functions fixed by the earlier domain-conflict migration are untouched.

The caller is `createNotificationForReminder` in `src/server/task-notifications.ts`, through a Supabase upsert into `motorist_notifications`. It runs from `materializeDueTaskReminders`, reached by the authorized notification materializer route, existing job registry and telephony cron. Both legacy40001 and PT409 follow its existing failed-delivery path before any email or push and record bounded application retry state. The materializer's aggregate HTTP response remains its existing contract; the HTTP409 asserted here is the underlying PostgREST notification write. No new application error mapping is required.

Validation uses a disposable local PostgreSQL17 database and PostgREST14. The seven tests in `tests/postgres/private-reminder-conflict-sqlstate.py` cover both rejection branches, valid and unrelated inserts, row-lock/reassignment ordering, HTTP409 with exactly one transaction attempt per refusal, successful HTTP201, exact authority metadata preservation, idempotent reapply and drift refusal. `src/server/task-reminder-conflict.test.ts` checks both SQLSTATEs prevent email/push and retain the delivery retry state. No shared database write or notification delivery is made by these tests.

This companion closes a remaining deterministic retry hazard; it is not evidence that this trigger caused the earlier rollback-count increase. A fresh81.6-second read-only production sample on2026-09-11 showed zero additional rollbacks and no lock waits. Apply only through the reviewed copy-specific migration workflow. No restart or session termination is part of this change.
