# Live layout preview — functionality preservation contract

Reviewed on 2026-09-12 against the dedicated `feat/live-layout-preview` worktree based on current `origin/dev`. This contract updates the earlier visual-only prototype: the live preview must render the existing application and its authorized data, with an optional visual treatment. It must not substitute the simplified demo model for the application model.

## Delivery and recovery

The preview uses the same `DispatchConsole`, case editors, providers, APIs and authorization boundaries as the existing application. The visual option must not select a second component tree, change React keys or remount editors. Switching back to the existing layout must be immediate and must preserve the selected case, unsaved fields, task/chat/note drafts, filters, sort order, panel sizes and widget preferences. Layout preference is browser-local; it is not a database migration.

The work branch receives a Vercel Preview. No production release or `dev` merge is part of this preview. Preview data belongs to this copy's existing shared Supabase project: an actual save is a real save for other testers. No new database, clone, seed, schema change, worker or telephony configuration change is required. Automated browser checks must use intercepted fixture APIs and must not perform writes against Preview or the shared database.

A visual fallback is not a database rollback: it restores presentation only and must never replace newer stored records with old snapshots. The previous visual prototype remains a separate reference artifact.

## Scope boundaries from the earlier prototype

The prototype's task reviewer/approval model, public recipient acceptance link and deterministic text-import demonstration are proposals. They are not existing live features and must not silently replace current task identities, due-date boards, case relationships, chat, reminders or SMS data. If they need server/schema work, keep them separate from this reversible visual preview and describe them honestly as pending functional development. Existing SMS templates, inbox/history, recordings and corrected transcripts already exist and must be reused.

The live layout may rename a presentation label or improve spacing, surfaces and controls, but such changes do not authorize deleting fields, collapsing a currently visible information row by default, weakening a validation or removing an action. Newly added widget behavior must be additive and preserve existing input syntax and keyboard operation.

## Test selection

`e2e/fixtures/compact-workspace.tsx` provides the complete real console with fake `DispatchData`, fake tasks and a service-worker stub. `compact-workspace.spec.ts` bundles it via esbuild and Tailwind, routes every browser request to isolated fixtures, aborts foreign origins and intentionally fails unhandled mutations. It is the primary harness for visual parity because it includes the existing application tree without live APIs.

`workspace-v3.spec.ts` provides richer writable fixture API state for task/note/draft and notification flows. `case-cockpit-v3.spec.ts` covers PDF/save ordering, revision conflicts and retained editors. `route-planner.spec.ts` covers actual Google-adapter interactions through fake services, including stale-response rejection. Reuse these before inventing a second UI or a second domain fixture.

Required evidence before sharing a live Preview: the changed unit tests, typecheck/build gate, isolated browser parity report with screenshots, no unhandled JS errors, and verification of the exact Vercel work-branch deployment. An authenticated read-only smoke may validate that real data renders; do not report live save, SMS send or physical calling as tested unless such a test was explicitly performed with the necessary authorization and evidence.

## SMS clarification from the live-preview discussion

The user reports that inbound SMS is not currently enabled. The useful primary flow is composing outgoing SMS from a case or without a case, then inspecting delivery/history. This is a product constraint provided by the user, not a claim that this read-only audit inspected deployed environment variables.

The existing `SmsComposerDialog.tsx` already supports case selection, an independent recipient with “Bez prípadu”, custom messages, templates, segment validation, explicit prepare/preview/send, stable request identity after uncertain delivery, task association and a History tab that switches between the selected case and all messages. `CaseSmsHistory.tsx` provides case-scoped history. `SmsHistory.tsx` keeps delivery state and location-request state separate and explicitly does not treat delivery as proof of reading. These existing flows must be retained.

Two presentation mismatches are present in the baseline: `DashboardPhone.tsx` chooses the inbox as the initial tab when an unread count exists, and `SmsComposerDialog.tsx` always displays “Prijaté SMS”. The preview should make outgoing composition the default and keep History directly accessible. Do not discard historical messages or imply that hiding an inbox disables provider processing. `context.repliesEnabled`, derived by `smsSender()` in `sms-channel.ts`, means the numbered reply channel is verified; it is not a separate reliable inbound-enabled capability. The server still has inbound webhook and inbox routes. A future capability-driven inbox presentation requires an explicit capability contract rather than treating this field as proof that receiving is disabled.

Relevant regression suites: `e2e/sms-composer.spec.ts`, `src/server/sms-workflow.test.ts`, `src/server/sms-inbox.test.ts`, `src/server/sms-channel.test.ts` and provider-status tests. Browser tests must intercept both reads and sends. Preserve the existing no-repeat-send/retry semantics, case selection and independent-message history.

## External center / colleague handoff: exact existing boundary

The only existing unauthenticated case-related token flow found in the route and migration inventory is the location request: `/l/[token]`, `/api/public/location-links/[token]`, `location-share-links.ts` and the `motorist_location_share_links` table. It hashes a random token, binds it to an organization/case with `scope = pickup_location`, applies expiry and accepts a normalized GPS submission with retry handling. Its public GET exposes only link state and expiry. It does not expose contact/vehicle information, accept or reject a case, assign an outside center, or allow case management.

The new handoff is therefore separate backend work. Reuse the audited token-generation/hash and expiry patterns where suitable, but never broaden an existing pickup token into permission to read or manage a case. A future handoff needs a separate grant scoped to one case and one defined external actor/center, a server-side field allowlist, explicit permissions, expiry/revocation, immutable decision history, conflict/idempotency handling and server-side validation for accept/reject with reason. Define “manage” as a limited list of permitted updates (for example proposed arrival or completion note), not access to internal tasks, costs, recordings, notes, directory or unrelated cases. The dispatcher's authorization and the external recipient's authorization are distinct.

The eventual “Copy link” and “Send by SMS” controls may reuse the existing SMS composer with an explicitly selected colleague recipient. A link opening is not acceptance, an SMS send is not acceptance, and the previously presented static local-storage demo is not a secure implementation. No production token, schema or external-access change is introduced by the visual preview.

## Implemented additive widget boundary

The optional calendar is now a view of the existing authorized task provider, rather than a second task model. It is hidden by default and available only when the preview is enabled; production does not gain a calendar setting or render its contents. Changing between classic and modern inside the preview retains calendar and other widget preferences. Calculator backspace is additive in the modern presentation; original expression parsing, parentheses, decimal comma, clear and copy remain. Note paper colors are derived presentation values and do not write private note records.

## Regression finding independent of the new layout

The existing `workspace-v3.spec.ts` scenario “successful case completion retains newer typing and saves it to the same case” was reproduced unchanged on detached `origin/dev` commit `6cbd23eb1769cfa99a5b694f2f5c4e2af1fe6b70`. It failed identically because its mock acknowledged a case save with the retired `dispatchData` response and omitted `mutationId`; the current client correctly retried the unacknowledged operation.

Only the fixture was corrected to the existing `detail-v2` contract: one canonical `caseDetail`, the echoed mutation ID and committed revision. The test now checks that completion and newer plate typing are two distinct mutations on the same case and that the second save uses the first committed revision. Its focused rerun passed. No case-save runtime or database behavior was changed to make the test pass. Baseline and corrected output are preserved in `.context/baseline-case-completion.log` and `.context/fixed-case-completion.log`.


## Final isolated parity result

`e2e/live-layout-preview.spec.ts`: **15 passed, 0 failed, 0 skipped** in the final integrated Chromium run. This includes the seven laptop/mobile/tablet viewport pairs above, all five case filters and eighteen table columns, same-instance case and task/chat drafts, note/calculator retention, horizontal/vertical resize and collapse, preference reload/invalid/denied storage, and outgoing-first SMS with standalone history. Screenshots include both visual styles and personalized tools in the full console at 1440 and 390 pixels.

A denied-storage test found a lazy React updater reading storage outside its enclosing try/catch; this was corrected by capturing the parsed preference inside the catch boundary before scheduling the updater. Manual screenshot review also found pale inherited telephony-status text on the new light header; scoped status colors were corrected and the desktop regression now checks a minimum 4.5:1 text contrast. Final output and source hashes are in `.context/live-layout-parity-final.json`, `.context/live-layout-parity-verification.md` and `.context/live-layout-parity-evidence.json`. This evidence is isolated browser/UI verification, not live provider or physical-device verification.
