# Call event contention repair — 13 September 2026

Target: the isolated Telnyx copy at https://dispecing-test.vercel.app/.

## Observed failure after the earlier latency release

The 09:12–09:18 UTC calls used the newly released code. One outgoing start improved from the earlier observed 7.44 seconds to 3.24 seconds. Nevertheless, hold/unhold requests still competed with simultaneous provider callbacks and exhausted their three-second ownership wait before issuing a command. Failed controls attempted ownership acquisition 13–17 times per request.

The bounded audit found 59 distinct webhook events with 148 deliveries and 46 recorded deferrals. The 95 webhook HTTP 5xx responses were delivery attempts, not 95 different lost events. Already-answered bridge confirmations issued no provider commands but still occupied the session while controls were waiting.

The earlier durable termination repair was working: three measured customer ends occurred 1.26–2.82 seconds after the persisted stop intent. However, one terminal webhook remained deferred and its customer leg was displayed as active for another 137 seconds until stale-state recovery. This was stale application state after physical termination. Recording and intro announcements remained disabled.

The header also classified any failed control notice as a disconnected/failed phone. A control operation can fail while the SDK remains registered. Browser reconciliation exposed a separate error boundary bug: its retryable ownership error became an HTTP 500.

## Changes

- Provider callbacks and opportunistic sweeps make one ownership attempt rather than repeatedly polling ahead of an operator. Interactive controls retain their bounded wait with increasing jittered delays. Ownership generation, command journal and database write fences remain authoritative.
- Completed webhook handlers and successful authenticated call actions replay a bounded number of exactly correlated deferred terminal/answer/bridge facts after releasing ownership. Terminal facts take priority. Existing ledger backoff is honored, including a freshly deferred fact that becomes eligible shortly after the owner finishes. Claims, failure budgets and fallback recovery remain in place; pending facts are not acknowledged as processed.
- Unrecorded passive media/conference observations use a minimal context when no recording, announcement or durable continuation needs the full routing configuration. Evidence, reducer, participant observation and audit processing remain intact.
- Real ownership contention has a distinct `session_busy` response with a Slovak message and a retry hint. Database/ownership failures remain separate errors. A busy reconciliation returns `reconciled: false` rather than claiming cleanup succeeded.
- Browser reconciliation keeps an independent in-flight guard, yields to commands on that session and uses bounded retries. Visibility changes cannot start duplicate verification requests.
- Selected in-call controls retry once only for the explicit pre-execution `session_busy` response, retaining the exact target and body. Unknown provider outcomes, network failures and call creation are not automatically resent. Ending or replacing the call invalidates an older waiting retry.
- The header presents a failed operation separately from actual SDK connection failure. Detailed operation errors remain visible. Immediate exact-call audio release from the previous repair is retained.
- Event timing includes ownership acquisition performed by the outer webhook handler; a zero inner wait no longer conceals that outer contention.

## Scope and verification

No migrations, live data corrections, routing changes, provider settings, recording changes, worker or scheduler deployments are part of this repair. No live customer calls or SMS are generated by automated tests. The local final gate passed 3,751 Vitest tests (2 existing skips), 43 Node tests (1 existing skip), TypeScript, changed-file ESLint and diff checks. The client verification covered 53 Chrome scenarios, including scoped retries and replacement/closure races. Exact deployment identities and deployed checks are recorded in the release pull requests.

Concurrent regressions reproduce a held session, simultaneous provider facts and controls, then recovery after ownership release. Browser regressions exercise failed reconciliation, visibility spam, bounded control retries and termination/replacement races. Real audio and carrier timing still require a fresh call after release; the observed timings above describe the preceding version and are not promises for every call.
