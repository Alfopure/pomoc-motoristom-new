# Partnerský web a konzultácie

Server-only partner module; it does not load dispatch data in `/partner`.

- UI: `PartnersModule({caseId?})`, `CasePartnerPanel({caseId})`; consultation and assistance links use `/?case=<uuid>`.
- APIs: office `GET/POST /api/partners`; partner list `GET /api/partners?portal=true`; authenticated output proxy `/api/partners/outputs/<id>?portal=true` (office omits `portal`). `preview=true` renders only the published fields.
- RPCs: `motorist_partner_actor`, `motorist_partner_accept`, `motorist_partner_read`, `motorist_partner_command`, `motorist_partner_membership_command`, `motorist_partner_report`. All are service-role-only with fixed search paths and fresh actor checks. The aggregate report uses a narrow SECURITY DEFINER function so it can count operation identities while operations base-table grants stay closed; the other partner RPCs use invoker privileges. Tables have RLS enabled with no browser grants. Published output and receipt tables deny service-role UPDATE/DELETE.
- Follow-up (`20261028120000_partner_case_followups.sql`, `followups.ts`): the office marks *Poistná udalosť* on a case with a saved partner context (`set_insurance` through `POST /api/partners`); the partner portal (`GET/POST /api/partners/portal`) lists only that partner's own cases through the exact allowlist in `motorist_partner_followup_projection` (number, date, type, coarse work status, make/model/plate; customer name and phone only for an insurance event), takes an insurance event, records client contact and appends its own notes. Status `new → taken → contacted`, absent row = revision 0, command receipts in `motorist_partner_followup_commands`. SECURITY DEFINER RPCs `motorist_partner_portal_cases`, `motorist_partner_followup_command`, `motorist_partner_followup_office_command`, `motorist_partner_followup_office_read` are service-role-only and re-check the office profile or current membership version; helpers are owner-only. The shared account is audited as the account (`actorKind: partner_account`), never as a person. Notes and receipts are append-only and never change the case or settlement. Unmarking or re-marking an insurance event is an office correction: the partner's status and taken/contacted history are kept; a re-mark starts a new marking time. Stats count cases by creation in `[from, to)`; taken/contacted count current insurance events; time to contact runs from insurance marking to recorded contact (`contactSample`), insurance events not yet contacted are `contactPending`, contacted ones without a measurable interval are `contactUnknown` — never zero. The portal list (max 200) puts every still-new insurance event first. The office route returns `followups: null` only when the follow-up RPC is missing (PGRST202/42883). Local contract: `python3 tests/postgres/partner-case-followups.py` (disposable cluster, all migrations).
- Migration: `supabase/migrations/20261026190404_partner_consultations_and_portal.sql`, followed by `20261026201554_partner_report_scoped_execution.sql`; report requires the accompanying shared-dispatch operations migration before activating the module. Private bucket: `motorist-partner-documents`; no signed/public download URLs.
- Invitations reuse only a verified existing organization account, or recover the deterministic account from its original invitation provenance. No dispatch profile is provisioned. Acceptance requires the latest unexpired invitation ID plus the authenticated matching user. Membership versions and shares are read anew for every portal read/download.
- Prices start unset; publication and email are separate explicit actions. Email provider acceptance is not delivery. An uncertain original intent is never automatically resent. A new operator intent gets a new receipt.

## Local validation

Use a fresh **local-only** database with the standard `anon`, `authenticated`, `service_role` roles already installed. `testing/schema.sql` is a minimal local fixture, not an application migration. Run the fixture, migration, and `security.sql` with `psql -v ON_ERROR_STOP=1`. Assertions cover independent payer/reference, idempotency/content conflicts, two deliberate assistance intents, reduced explicit shares, org/version/share revocation, invitation generations/expiry, same field account without dispatch profile, public grants, and the 3-call / 1-consultation / 2-operation report. Test data rolls back.

`pnpm exec vitest run src/server/partners/access.test.ts src/components/auth/login-destination.test.ts src/server/access-management.test.ts src/server/towing/memberships.test.ts` verifies provisioning provenance and existing auth regressions without contacting providers.

## Remaining inputs and limits

Actual partner contacts, recipient addresses and approved prices require owner input. The accident-report template is a separate blocked product input. No external invite, email or PDF delivery was exercised by local tests. New web cases save partner origin together with the case, related rows, history and receipt through `motorist_create_case_atomic` (`20261026211759_atomic_case_partner_origin.sql`); a lost response retries the frozen original creation command. The immutable context is never guessed from a line label or phone number. Portal lists are bounded to the latest 100 published versions; the office report aggregates all consultations independently of that display bound.

`PartnerDraftProvider` retains each case's unpublished fields and pending command in the current workspace session while modules or keyed case panels unmount. It writes no browser storage. Uncertain commands retain their entire original body and ID, block a new intent for that case, and can be verified through the existing navigation guard or the explicit retry control. Leaving that guard does not erase an uncertain command. Refresh/closing the document warns about remaining drafts; a new authenticated workspace starts with an empty cache. Refreshing confirmed server data does not overwrite an edited settlement.
